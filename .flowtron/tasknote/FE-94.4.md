# FE-94.4 | Collapse App's repeated warning badges and diagnostic strips into components

[← PLAN.md](../PLAN.md) · 🌱 Starter (filed 2026-08-23)

## 🌱 Starter context

_Captured 2026-08-23 during the `/ft-refactor viz/src/ui/App.tsx` depth survey — promote to full tasknote at `/ft-task` checkout._

### Why this exists

`App.tsx` carries two families of duplicated JSX, ~85 lines between them:

- **Four header badges** (lines 340-359: unparsed, duplicate epics, near-miss
  headings, live-updates-off) each repeating the same 9-class amber `<span>`
  verbatim, differing only in the copy.
- **Three diagnostic strips** (lines 446-493: unparsed, duplicate epics,
  near-miss headings) each repeating the same amber container, the same
  singular/plural `<p>`, and the same `<ul className="mt-1 font-mono text-sm">`
  list, differing only in copy and the key/label of each `<li>`.

Extracting them first shrinks what FE-94.5 has to move by roughly a third and
gives the header a clean composition boundary to move across. Lowest-risk step
in the sequence: pure JSX, no state, no hooks.

### Solution shape

- `viz/src/ui/HeaderBadge.tsx` — presentational, children-only, owning the
  shared amber className. Four call sites become one-liners.
- `viz/src/ui/DiagnosticBanner.tsx` — takes the message node and the list
  items (or renders `children` for the `<ul>`), owning the amber container.
  Three call sites collapse.
- Rendered DOM must be byte-identical: the diagnostics tests assert on badge
  text and strip content (`App.test.tsx:1002`, `:1033`, `:1073`), and the
  board test at `:917` queries by `.overflow-x-auto` — className drift is
  a real failure mode here, so keep every class string as-is.
- The error banner (red, line 430) and the SSE banner (amber, `role="status"`,
  line 436) are single-instance and shaped differently — leave them inline
  unless promotion finds the abstraction genuinely fits.
- Acceptance seeds for Phase 1 to promote into `## ✅ Acceptance`:
  - the full suite including FE-94.2's additions green **before** and
    **after**, unchanged;
  - behavior-preserving, no feature change, no visual change;
  - `App`'s public surface unchanged;
  - `npm --prefix viz test`, `run typecheck`, `run lint` green.

### Files to touch (preliminary survey — drift-check at promotion)

- `viz/src/ui/HeaderBadge.tsx` — new.
- `viz/src/ui/DiagnosticBanner.tsx` — new.
- `viz/src/ui/App.tsx` — seven call sites collapse; imports adjusted.

### Explicitly out of scope

- The header block as a whole — FE-94.5.
- The error and SSE-disconnect banners (single-instance, different shapes).
- Any restyling, token migration, or `constants.ts` palette work — this is a
  move, not a redesign.
- Data-driving the three strips off a single diagnostics array; that is a
  behavior-shaped change, not a de-duplication.

### Decisions locked in this conversation

| Decision | Choice | Rationale |
|---|---|---|
| Two components, not one | `HeaderBadge` + `DiagnosticBanner` | The badge is an inline span in a `<p>`; the strip is a block section — different call contexts |
| Class strings | Copied verbatim | Tests and visual output both depend on them; a "tidy while I'm here" pass would break the behavior-preservation contract |
| Ordering vs FE-94.5 | Badges first | Shrinks the header move and gives it composed pieces to carry |

### Open at promotion (Phase 1 should resolve)

- Does `DiagnosticBanner` take `items: ReactNode[]` or render `children`
  inside its own `<ul>`? Lean: `children`, since each strip keys its `<li>`
  differently (`u.line`, `${d.id}-${i}`, `h.line`).
- Do the badges belong in `constants.ts` as a token instead of a component?
  Lean: no — it is markup plus a class, not a token.
