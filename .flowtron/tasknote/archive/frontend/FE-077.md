# FE-077 | plan-parser-regex-tighten

[← PLAN.md](../PLAN.md) · 🟢 In progress

## 🎯 Goal

Bound `TASK_LINE`'s two trailing adjacent lazy optional capture groups in `viz/src/parser.ts` to `[^\n]+?` to remove their super-linear backtracking shape on long non-matching lines.

## ⚡ Notes

**Relevance:** Proceed — single-regex-line change, theoretical hardening only (trusted local PLAN.md input), no design tradeoffs.
**Best Practices Review:** N/A — mechanical character-class tightening on an existing regex; no new abstraction, no responsibility shift, no capture-group change (group count/order unchanged, confirmed by the unmodified 57-test parser suite).
**Drift check:** Path matches. `viz/src/parser.ts:58-59` still defines `TASK_LINE` with the shortname group `(?:\s+\|\s+(.+?))?` and long-description group `(?:\s+[—-]\s+(.+?))?` immediately adjacent before the terminal `\s*$` — exactly the shape the PLAN line cites.
**Archive skim:** `TASK_LINE` has an active evolution history: FE-044 added `[!critical]`; FE-066 added three non-capturing decorative-glyph tolerances (stacked `[model]`, suggestion glyph, leading status glyph); FE-067 extended ID-shape tolerance for legacy bold-label lines; FE-063.2 built `parsePlanWithDiagnostics` on top so lines failing `TASK_LINE` surface as "unparsed" instead of silently dropping. None touched the trailing shortname/description groups directly — load-bearing constraint carried forward: this fix must not shift capture-group count or order (all three prior tasks were explicit about preserving that).
**Pattern survey:** No sibling shape to extend — `TASK_LINE` is the sole regex of this kind in the file. `[^\n]+?` mirrors the audit finding's literal suggested pattern and is a common ReDoS-hardening idiom (explicit negated-newline class vs. bare `.` even where behaviorally equivalent under JS's default non-`s`-flag semantics for single-line input).
**Implementation:** Changed both trailing capture groups in `TASK_LINE` (`viz/src/parser.ts:59`) from `(.+?)` to `([^\n]+?)` — shortname group (after `| `) and long-description group (after `— `/`- `). No other part of the regex touched; capture-group count/order/semantics unchanged.
**Docs touched:** no change — the inline grammar comment above `TASK_LINE` (lines 41-57) describes captured fields and tolerances, not the underlying character-class choice; nothing there went stale.
