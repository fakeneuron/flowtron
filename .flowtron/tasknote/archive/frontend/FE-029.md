### Failure mechanism (working hypothesis)

The retry succeeds, which rules out *deterministic content-based* parse failure (a malformed file would fail both times). The bug is *timing-dependent*. Two plausible mechanisms, neither requiring a code-level reproduction in this task:

1. **libuv thread pool saturation under chokidar polling.** With `usePolling: true, interval: 200, depth: 2`, chokidar's polling thread runs `fs.stat` against every watched path on each tick. Combined with 50-700 concurrent `readFile` calls from the first `/api/archive` request, libuv's default 4-thread pool may queue an op long enough that something transient (mtime change mid-read?) trips gray-matter on partial content.
2. **gray-matter on a specific file with marginal frontmatter.** Some adopter archive tasknotes may have whitespace, BOM, or YAML quirks that gray-matter parses non-deterministically. Less likely given the retry succeeds, but instrumentation will tell us if any file shows up repeatedly in the logs.

Either way, the durable fix is the same: per-file try/catch inside `readArchive` so a single failure doesn't kill the load. The `console.error` instrumentation tells us *which* files fail and whether failures are clustered (mechanism 2) or spread randomly (mechanism 1). The fix is non-destructive — if every file always succeeds, the new code path is dead weight; if any fails, we recover gracefully and log the diagnostic.

**Implementation Notes:**

### Pattern survey

The fix lands in one function, `readArchive` in `viz/src/archiveCache.ts:16-34`. Neighboring patterns:

- `vite.config.ts:128-152` (`/api/active` handler) does the same `readFile + parseTasknote` per file, also with `Promise.all`, also without per-file tolerance — but it's out of scope for FE-029 (active tasknote count is tiny per project, no observed cold-start failure).
- `archiveCache.ts:42-55` (`createArchiveCache.get`) already has an error-no-poison `.catch` guard that removes a rejected entry from the cache. With per-file tolerance the guard becomes effectively dead code (`readArchive` no longer rejects from per-file failures) but the guard is preserved as defense-in-depth — a future change that re-introduces a non-per-file rejection path (e.g., `safeReaddir` flipping to throw) still wants the no-poison behavior.
- Existing test file `archiveCache.test.ts` already had the right `tmpdir + makeProject` setup; the new test extended that shape directly.

### Files changed

- **`viz/src/archiveCache.ts`** (~9 LOC delta): wrapped the per-file `readFile + parseTasknote` in `try/catch`. On error: `console.error('[archiveCache] failed to read/parse <path>: <message>')` and return `null`. Added `.filter((t): t is Tasknote => t !== null)` after `nested.flat()` so the failed slots drop. Null-filter location chosen at the post-`flat()` outer (one call, simpler) over per-area (two-step filter+flat). Logging goes to stderr via `console.error` — no new structured surface.

- **`viz/src/archiveCache.test.ts`** (~25 LOC delta): replaced the now-obsolete `does not poison the cache when a populate fails` test (which relied on rejection that no longer happens with tolerance) with **two** new tests:
  - `drops files with malformed frontmatter and returns the rest` — three-file setup (two valid + one malformed YAML with a tab-indent), asserts the cache returns only the two valid IDs and the malformed file is dropped silently (stderr instrumentation confirmed by vitest output).
  - `recovers a dropped malformed file once it is fixed and the cache invalidates` — single-file malformed setup; first `get()` returns `[]` (no throw); after writeFile + explicit `cache.invalidate`, second `get()` returns the now-valid tasknote. This covers the "recovery after fix" path; in production the chokidar SSE watcher calls `invalidate` on disk writes automatically.

### Design decisions

- **Drop failed rows (vs degraded placeholder)**: preserves `Tasknote[]` shape; no new UI state. The viz simply renders fewer archive rows on the affected project until the next refresh. User-locked at Discovery.
- **`console.error` to stderr (vs structured surface)**: zero-ceremony; the dev server already writes to stderr; promotion to a structured registry can land as a follow-up if instrumentation surfaces a recurring deterministic failure.
- **Null-filter after `.flat()` (vs per-area inner filter)**: one extra call instead of mutating the inner area Promise.all return shape; minimal-diff.
- **Keep the no-poison `.catch` guard**: defensive scaffolding. `readArchive` no longer rejects from per-file failures, but the guard still earns its keep if a future change widens the rejection surface (e.g., `safeReaddir` semantics changing).

### Non-obvious gotcha encountered (debugging trail, recorded for future test authors)

gray-matter (the YAML frontmatter parser) **caches parse results by input string**. Two test fixtures with identical malformed content will produce different results: the first call throws (uncached), the second returns `{ data: {}, content: <whole input> }` without throwing (cached). This caused an initial false-negative in the second test (`recovers a dropped malformed file...`) before discovery: vitest ran multiple tests in the same process, and the second test's fixture content was identical to the first's, so gray-matter's cache short-circuited the throw. Resolution: use **distinct malformed YAML content per test** (tab-indent for the first, unclosed flow collection for the second). Documenting this here so the next test author doesn't waste a half-hour on the same trap.

**Final Summary:**

`viz/src/archiveCache.ts:readArchive` no longer collapses a 700-file archive load into a single 500 when any one file's `readFile + parseTasknote` fails. Each per-file async is now wrapped in `try/catch`: on error, `console.error` emits `[archiveCache] failed to read/parse <abs-path>: <error.message>` to dev-server stderr, and the failed slot is dropped via a post-`flat()` null filter. FE-016's "transient YAML parse error on the very first request post-startup — did not reproduce" note from 2026-05-07 is now resolved-by-instrumentation: if it recurs, the failing file is named in stderr; if it doesn't, the tolerance fix is silently dead-weight.
