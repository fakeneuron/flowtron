# FE-071 | viz-frontmatter-eval-guard

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[RELATED]]

## 🎯 Goal

Disable gray-matter's javascript/js frontmatter engine in `viz/src/tasknote-parse.ts` so a `---js` frontmatter block in a tasknote can no longer trigger code execution in the dev server.

## ✅ Acceptance

- [ ] `viz/src/tasknote-parse.ts` passes an `engines` override to gray-matter that throws (or otherwise rejects) on the `javascript`/`js` engine
- [ ] Regression test proves a `---js` fenced frontmatter block no longer executes and is handled gracefully (parse error / fallback), not silently eval'd

## 🧩 Subtasks

- [ ] Pass an `engines` override to `matter(text, ...)` in `viz/src/tasknote-parse.ts` that overrides the `javascript` engine key with a function that throws (covers both `---js` and `---javascript` fences via gray-matter's alias resolution)
- [ ] Add a regression test in `viz/src/tasknote.test.ts` proving a `---js` frontmatter block's code never executes (global side-channel marker stays unset) and that `parseTasknote` throws, consistent with existing malformed-frontmatter handling
- [ ] Run targeted test suite + typecheck + lint on the two changed files

## 🔗 Related

- [[FE-019]] — first flagged gray-matter's `engines.js` `eval` usage as a Vite build warning (not actionable then)

**Discovery Notes:**

- `viz/src/tasknote-parse.ts:11` calls `matter(text)` with no options. Installed `gray-matter@4.0.3`'s built-in `javascript` engine (`node_modules/gray-matter/lib/engines.js:36-54`) parses a `---js`/`---javascript` fenced frontmatter block via `eval()` on the raw block content — genuine server-side code execution if a tasknote markdown file (or its frontmatter) is attacker-influenced. `lib/engine.js` resolves `js`/`javascript`/`coffee`/`cson` aliases all onto the same `options.engines[name]` lookup, and `lib/defaults.js:16` does `Object.assign({}, engines, opts.parsers, opts.engines)` — so a caller-supplied `engines.javascript` cleanly overrides the default and is not itself cached (gray-matter's internal cache in `index.js` is skipped whenever `options` is passed).
- `viz/src/devApi.ts:83-91` and `viz/src/archiveCache.ts:19-28` both already wrap their `parseTasknote()` calls in try/catch and silently skip the file on any thrown error (documented behavior for malformed YAML per FE-029: "Malformed frontmatter throws synchronously... not modified"). So making the `javascript` engine throw is safe end-to-end — it degrades to the same already-tolerated "skip this one malformed tasknote" path, not a crash.
- Archive skim: **FE-026** split `parseTasknote` into this server-only module and explicitly flagged "Vite warned `gray-matter`'s `engines.js` uses `eval` — known transitive issue, not actionable in viz/" as out of scope at the time. **FE-019** first surfaced the same build-time warning. **FE-029** independently documented (for an unrelated flakiness investigation) that `parseTasknote` "may throw via gray-matter" and that this is already tolerated by both call sites, and separately warned that gray-matter caches parse results by input string when no `options` are passed — irrelevant here since our fix always passes `options.engines`, which bypasses the cache path per `index.js`.

**Implementation Notes:**

Overriding only the `javascript` key in `options.engines` is sufficient: gray-matter's `lib/engine.js` `aliase()` maps both `js` and `javascript` fence names onto the same `javascript` lookup key before consulting `options.engines`, so one override closes both spellings. `coffee`/`cson` aliases point at an engine gray-matter doesn't ship by default (already unregistered, already throws) — out of scope, no change needed there.

**Final Summary:**

Disabled gray-matter's built-in `javascript`/`js` frontmatter engine in `viz/src/tasknote-parse.ts` (the sole `gray-matter` call site, server-only per FE-026), closing an `eval()`-based code-execution path first flagged as a build-warning curiosity in FE-019 and left "not actionable" in FE-026 — this audit (2026-07-26, Finding #1, Medium) confirmed it as a live exploit path: `matter(text)` with no options let a `---js` fenced frontmatter block run arbitrary JS server-side via gray-matter's default `engines.javascript` (`eval()`, per `node_modules/gray-matter/lib/engines.js:36-54`).

**Fix:** `matter(text)` → `matter(text, { engines: { javascript: DISABLED_JS_ENGINE } })`, where `DISABLED_JS_ENGINE` unconditionally throws. One override closes both `---js` and `---javascript` fences — gray-matter's engine-alias resolution (`lib/engine.js`) maps both fence names onto the same `engines.javascript` lookup key. The resulting throw is not a new failure mode: both call sites (`devApi.ts`, `archiveCache.ts`) already catch and skip on any `parseTasknote` exception, a path FE-029 previously documented and validated for malformed-YAML frontmatter.
