# FE-012 | viz inbound wikilink back-refs

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[FE-007]]

## 🎯 Goal

Surface inbound `[[wikilink]]` references in the viz: when other tasks point at a target task (via `related-tasks:` frontmatter or PLAN long-description), the target's row gets a "← referenced by N" chip.

## ✅ Acceptance

- [x] Inbound-reference map is computed once per data load (memoized on `tasks` + `tasknotesById`).
- [x] Sources counted: `Task.relatedTasks` (PLAN long-description `[[ID]]` mentions, blocked-by stripped) + `Tasknote.frontmatter.relatedTasks`.
- [x] `Task.blockedBy` is **not** a source (`BlockerChip` already covers that signal).
- [x] Same source counted once even when listed in both the PLAN line and the frontmatter (`Set`-based dedup).
- [x] Self-references are excluded.
- [x] New `BackRefChip` renders only when N ≥ 1; chip text reads `← referenced by N`.
- [x] Clicking the chip toggles the row's `TaskDetail` (same affordance as clicking the row body); chip is keyboard-focusable.
- [x] Chip renders on standard `TaskRow` and on `EpicRow`'s `TaskRowInner`; **not** on `SubtaskRow` (out of scope per task line).
- [x] One new automated test asserts the chip count for a fixture where a task is referenced by ≥ 2 other tasks.
- [x] `npm run typecheck` clean; full vitest suite green; visual confirmation in the dev server (e.g. `FE-007` shows back-refs from recent FE tasks that wikilinked it).

**Discovery Notes:**

**Clarifications resolved (via AskUserQuestion):**

- **Source set.** Count `Task.relatedTasks` + `frontmatter.relatedTasks`; **exclude** `Task.blockedBy`. The blocked-by relationship already has its dedicated `BlockerChip` on the blocked task's row — keeping back-refs to "general references only" preserves chip semantics (one chip = one relationship type).
- **Click behavior.** Chip click toggles the row's `TaskDetail` panel — same affordance as the row body. Cheap, no new popover state machine; the user can already discover referrers via the description / related-tasks UI inside detail.
- **Label.** `← referenced by N` (verbatim from the PLAN line). Self-explanatory at a glance; consistent with the task author's phrasing.

**Implementation shape (decided in Phase 1, executed in Phase 2):**

- New helper `buildInboundRefs(tasks, tasknotesById): Map<string, Set<string>>` in `viz/src/ui/utils.ts` (existing home for shared row-prep helpers like `effectiveStatus`, `groupBy`). `Set<string>` value (not just a count) so the helper stays useful if a future task wants to list referrers; `TaskRowInner` reads `.size` for the chip text.
- Computed once in `App.tsx` via `useMemo([tasks, tasknotesById])`. Threaded as a single `inboundRefs` prop through `PrioritySection` → `TaskRow` / `EpicRow` → `TaskRowInner`. Same propagation shape as `tasknotesById`.
- New `viz/src/ui/BackRefChip.tsx` mirroring `RelatedChip.tsx`'s minimal shape (single-element button, hover state, `title=`). Renders `← referenced by {N}`. `onClick` is plumbed through `TaskRowInner`'s existing `onToggleDetail` — no new handler chain.
- Chip placement in `TaskRowInner`: right-side chip group, immediately after the `RelatedChip` cluster — outbound refs and inbound refs sit visually adjacent, mirroring the existing `BlockerChip` (left group) / `RelatedChip` (right group) topology.
- `SubtaskRow` is intentionally out of scope: the PLAN line names `TaskRowInner` as the render site, and `SubtaskRow` is the deliberately-spartan epic-child renderer (no chip cluster). Subtasks that get referenced still appear in their parent row's chips when the parent is referenced; isolated subtask back-refs are rare enough that the simpler scope wins.

**Implementation Notes:**

Six-file change, all in `viz/src/ui/` plus the helper in `utils.ts`:

- `viz/src/ui/utils.ts` — added `buildInboundRefs(tasks, tasknotesById): Map<string, Set<string>>`. Iterates tasks for `Task.relatedTasks` (parser already strips blocked-by from this list) and `tasknotesById` values for `frontmatter.relatedTasks`. Set-valued for free dedup when the same source appears in both PLAN long-description and frontmatter.
- `viz/src/ui/App.tsx` — added `useMemo([tasks, tasknotesById])` calling `buildInboundRefs`; passes the result through to `PrioritySection`.
- `viz/src/ui/PrioritySection.tsx`, `TaskRow.tsx`, `EpicRow.tsx` — added `inboundRefs` prop and forwarded to `TaskRowInner`.
- `viz/src/ui/TaskRowInner.tsx` — accepts `inboundRefs`, computes `inboundCount = inboundRefs.get(task.id)?.size ?? 0`, renders `<BackRefChip count={inboundCount} onClick={onToggleDetail} />` when `inboundCount > 0`. Chip placement: right-side chip cluster, immediately after the outbound `RelatedChip` block, before due/status. Also extended the `showNoTasknote` guard to require `inboundCount === 0` — otherwise a referenced row with no tasknote would show both "no tasknote" and "← referenced by N" which reads as contradictory.
- `viz/src/ui/BackRefChip.tsx` (new) — button, `← referenced by {count}`, `title="{N} task(s) reference this"` (singular/plural). Single-click → `onToggleDetail` (the row's existing detail-toggle handler).

**Decisions surfaced via AskUserQuestion (logged in Discovery Notes):**

- Source set: related-only — `Task.relatedTasks` + `frontmatter.relatedTasks`. `Task.blockedBy` excluded.
- Click behavior: opens the row's `TaskDetail` panel (no new popover state machine).
- Label: verbatim `← referenced by N`.
