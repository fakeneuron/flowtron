# FE-079 | selector-menu-aria

[← PLAN.md](../PLAN.md) · ✅ Completed

## 🎯 Goal

Fix the `ProjectSelector` overflow dropdown's ARIA role mismatch — the `role="menu"` container holds plain `<button>` children (no `role="menuitem"`, no arrow-key navigation), which violates the WAI-ARIA menu pattern.

## ⚡ Notes

**Relevance:** Proceed — single-file ARIA fix, matches PLAN.md line and audit finding exactly.
**Best Practices Review:** N/A — no refactor; swapping one attribute value and its two test-side references, no new abstraction or duplication introduced.
**Drift check:** `viz/src/ui/ProjectSelector.tsx` still has the exact shape PLAN.md describes — `role="menu"` container at line 129, chip buttons via `renderChip` (line 70) with no `role="menuitem"` and no `onKeyDown` menu navigation. No contradiction with SPEC.
**Archive skim:** `FE-068` (archive/frontend/FE-068.md) is the origin of this dropdown — it added `role="menu"` deliberately to "match the tab bar's own border/shadow language" but did not analyze full ARIA menu-pattern requirements (arrow-key nav, `menuitem` children). It also documents the sibling **visible** chip-group already uses `role="group"` (line 105) for the same kind of selectable-button strip — that's the precedent this fix extends.
**Pattern survey:** Extends the existing sibling pattern in the same file — the inline visible-chip container already uses `role="group"` + `aria-label` for a labeled group of toggle buttons (line 104-106). Applying the same `role="group"` to the overflow dropdown container is consistent with how this component already models "a labeled group of selectable buttons," rather than introducing net-new arrow-key menu navigation for a widget that doesn't behave like an OS menu (click-to-select, not command execution).
**Implementation:** Changed `viz/src/ui/ProjectSelector.tsx:129` `role="menu"` → `role="group"` on the overflow dropdown container (chips keep their plain `<button>` role — no `menuitem` needed under `group`). Updated `viz/src/ui/ProjectSelector.test.tsx` (3 tests, 6 call sites) from `getByRole('menu', ...)` / `queryByRole('menu')` to `getByRole('group', { name: 'More projects' })` / `queryByRole('group', { name: 'More projects' })` — the accessible-name filter is required now (not just style) because the pre-existing inline chip-group also uses `role="group"` (`aria-label="Project"`), so a bare `getByRole('group')` would match two elements once the dropdown is open. `aria-haspopup="true"` / `aria-expanded` on the `+N` toggle button left as-is — not part of the audit finding, and `aria-haspopup="true"` is a generic "has an expandable popup" signal, not menu-exclusive in practice.
**Docs touched:** No change — no AI-referenced doc describes this component's ARIA contract.

## ✅ Recap

Fixed the ARIA role mismatch in `ProjectSelector`'s overflow dropdown: `role="menu"` (no `menuitem` children, no arrow-key nav) → `role="group"`, matching the sibling inline chip-group's existing pattern in the same file. Updated 3 test assertions from `role('menu')` to `role('group')` to match. `npm --prefix viz run lint`, `npm --prefix viz run typecheck`, and `npm --prefix viz test` all pass (245/245, 18 test files, ProjectSelector suite 11/11 green). No design tradeoffs; single-file + single-test-file change.
