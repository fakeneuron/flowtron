# FE-063.4 | order-independent-grouping

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[FE-EPIC-063]]

## 🎯 Goal

Make `groupTasks` attach subtasks to their epic parent regardless of list order, so a hand-authored PLAN.md with a subtask line above its epic line still nests correctly.

## ✅ Acceptance

- [ ] `groupTasks` uses a two-pass approach (index epics first, then attach children) so subtask-to-epic attachment no longer depends on the epic appearing before its children in the input array
- [ ] New test covers a subtask listed above its epic in the input array and confirms it still nests as a child

## 🧩 Subtasks

- [ ] Rewrite `groupTasks` as two passes: pass 1 indexes every epic task into `epicByKey`; pass 2 walks tasks in original order, pushing epic nodes to top-level `nodes` and attaching subtasks to their epic's `children` (or as standalone if no matching epic exists)
- [ ] Add a test case with a subtask listed above its epic in the input array, asserting it still nests as a child
- [ ] Run `viz` test suite + lint/type-check on changed files

## 🛠️ Phase 2: Execution

- [x] **Pattern survey** — kept the existing single-function shape; no neighboring two-pass pattern needed importing, just restructured the loop body into two passes over the same `epicByKey` map.

- [x] Implemented the minimal solution

**Implementation Notes:**

- `viz/src/parser.ts:124-149` (`groupTasks`): split into two passes over `epicByKey`. Pass 1 walks `tasks` once, creating a `TaskNode` for every epic and indexing it by `epicKey(task.id)`. Pass 2 walks `tasks` again in original order — epics are pushed to the top-level `nodes` array at their own position (reusing the pass-1 node object), subtasks look up their parent via `epicByKey` (already fully populated) and are appended to `children`, and unmatched IDs fall back to standalone nodes. This decouples subtask-attachment from iteration order while keeping top-level ordering anchored to each epic's own line position.
- `viz/src/parser.test.ts`: added `'attaches a subtask to its epic even when listed above the epic'` — `[CORE-009.1, CORE-EPIC-009, CORE-009.2]` input, asserts both subtasks nest under the epic in order. The existing `'treats orphan subtasks (no matching epic) as top-level rows'` case (no epic present at all) is untouched and still passes, confirming true orphans aren't accidentally captured.
