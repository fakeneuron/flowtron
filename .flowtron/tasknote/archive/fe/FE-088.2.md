# FE-088.2 | realpath containment

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[FE-EPIC-088]] · [[CORE-222]] · [[CORE-431.2]] · [[FE-047]]

## 🎯 Goal

Make `discoverProjects` and `archiveCache.readArchive` drop any file whose
realpath resolves outside its project root, so a symlinked `PLAN.md`,
`.flowtron/`, or `archive/` cannot make the viz dev server read and serve a
file from anywhere on disk — while symlinked *project roots* keep working.

- [x] `viz/src/fsSafe.ts` exports a containment primitive (`safeRealpath` + `realpathWithin`) alongside `safeReaddir`, with unit tests
- [x] `discoverProjects` skips a candidate whose `.flowtron/PLAN.md` resolves outside the project root's realpath
- [x] `archiveCache.readArchive` skips any archive `.md` whose realpath resolves outside the project root's realpath
- [x] `devApi.createActiveHandler` applies the same containment to `/api/active` reads (scope widening approved at the 🛠️ gate)
- [x] A symlinked project root (`~/code/foo -> /elsewhere/foo`) is still discovered and its archive still read — the [[CORE-222]] / [[CORE-431.2]] invariant holds

**Discovery Notes:**

**Read set.** `viz/src/workspace.ts` (`discoverProjects`, `isFile`,
`readFlowtronVersion`), `viz/src/archiveCache.ts` (`readArchive`),
`viz/src/fsSafe.ts` (`safeReaddir`), `viz/src/devApi.ts` (all five handlers),
`viz/vite.config.ts` (wiring), `SECURITY.md` §"Visualizer (`viz/`)
dev-server scope".

**What is already closed.** `readdir(..., { withFileTypes: true })` reports
symlink entries with `isSymbolicLink() === true` and both `isFile()` and
`isDirectory()` `=== false` (verified empirically). So `readArchive`'s
existing `areas.filter(e => e.isDirectory())` and
`files.filter(e => e.isFile())` **already** drop a symlinked area dir and a
symlinked `FE-001.md`. The dirent layer is not the hole.

**What is open.** The hole is at *ancestor* level, where `readdir`/`stat`
follow the final component:

1. `discoverProjects` — `isFile(planPath)` uses `stat`, which follows. A
   symlinked `.flowtron/PLAN.md` (or symlinked `.flowtron/`) pointing
   anywhere on disk makes the dir a "project", and `createPlanHandler`
   then serves that file's raw bytes at `/api/plan?project=<name>`.
2. `readArchive` — `safeReaddir(project.archiveDir)` follows a symlinked
   `archive/` (or symlinked `tasknote/` / `.flowtron/`). Real `.md` files
   under the target are then read and returned by `/api/archive`.

**Why the base must be the project root, not the archive dir.** Containment
relative to `archiveDir` would be vacuous for case 2 — if `archiveDir`
itself is the symlink, everything under its target is trivially "inside" it.
The PLAN line's wording ("resolving outside **the project root**") is the
correct and stronger base, and it is what this task implements.

**Archive skim (`archive/fe/`, `archive/core/` — grepped `workspace.ts`,
`archiveCache.ts`, `fsSafe.ts`, `discoverProjects`, `readArchive`,
`symlink`, `realpath`).** No prior task has touched path containment
(`realpath` returns zero hits across the archive). Two load-bearing prior
decisions constrain the fix:

- **[[CORE-222]]** — `usePolling: true` exists *because* `discoverProjects`
  deliberately includes symlink entries: adopter project roots under
  `~/code` can be symlinks, and macOS FSEvents does not fire reliably
  inside them.
- **[[CORE-431.2]]** — the hot/archive watch split re-affirms the same
  assumption ("`discoverProjects` includes symlink entries", "symlink miss
  is covered by the hot-path `unlink`").

⇒ **Hard constraint:** a symlinked project root must stay discoverable.
Containment therefore resolves the project root *first* and checks children
against the resolved root — it never requires the root to live physically
inside the workspace dir. Naive "realpath must stay under
`FLOWTRON_VIZ_WORKSPACE`" containment would silently un-discover half the
fleet; that is the trap this note records.

- **[[FE-048]]** added `readFlowtronVersion(<root>/.flowtron/core/SPEC.md)`
  to `discoverProjects`. Deliberately left **outside** containment: it
  extracts only a `v\d+\.\d+\.\d+` regex match (no content reaches the
  wire), and `.flowtron/core -> ~/code/flowtron` is a plausible local-dev
  symlink that containment would break for zero security gain.
- **[[FE-047]]** / [[FE-029]] — established the silent-skip + stderr-log
  convention for unreadable files in these two functions. A containment
  drop is the same shape: skip the row, no client-visible error.

**Drift check.** Cited symbols match current code: `discoverProjects`
(`viz/src/workspace.ts:72`), `readArchive` (`viz/src/archiveCache.ts:8`).
Both still have exactly the shape Finding #2 describes. Against the parent

**One live doc contradiction found.** `SECURITY.md` §"Visualizer (`viz/`)
dev-server scope" currently asserts *"Reads files only from projects
discovered under `${FLOWTRON_VIZ_WORKSPACE:-~/code}/*/.flowtron/`"* — which
is precisely the claim the symlink escape falsifies today. This task makes
the sentence true and updates it to say the bound is enforced. `SECURITY.md`
is therefore a deliverable path, not just a doc-drift sweep entry.

**Best Practices Review.** Touched responsibilities: `fsSafe.ts` is the
existing home for tolerant fs primitives (`safeReaddir`) — the containment
helpers belong there, not duplicated into two call sites. Dependency
direction preserved (`workspace.ts` and `archiveCache.ts` both already
import from leaf modules; `fsSafe.ts` imports nothing local). No refactor of
existing code required; the change is additive. Deferred cleanup: none
identified.

**Scope note — resolved at the 🛠️ gate.** `devApi.createActiveHandler` reads
`<root>/.flowtron/tasknote/*.md` with the identical unbounded pattern and is
*not* named in the PLAN line. Surfaced at the exit gate; operator chose to
**include** it, so `viz/src/devApi.ts` joins the diff. Rationale accepted:
closing `readArchive` while leaving an identical hole one file over would not
actually "close the symlink read", and [[FE-088.N]] would flag the asymmetry.

**Clarifications.** One asked (scope, above; answered *include `/api/active`*).
Assumptions otherwise: (1) containment failures drop silently, matching the
existing convention; (2) descriptor fields (`root`, `planPath`, …) keep
their un-resolved values so callers and the existing exact-equality test are
unaffected; (3) the residual realpath→readFile TOCTOU window is accepted for
a loopback-only single-user dev tool.

**Implementation Notes:**

**Pattern survey.** `viz/src/fsSafe.ts` is the established home for tolerant
fs primitives (`safeReaddir`: try / return-empty, never throw). The two new
exports extend that shape rather than introducing a parallel one:
`safeRealpath` is `safeReaddir`'s null-returning sibling, and
`realpathWithin` composes it with a pure path predicate. Both call sites then
follow the module's existing silent-skip convention ([[FE-029]], [[FE-047]]):
drop the row, log nothing to the client. No new module, no new dependency.

**Minimal refactor gate.** Nothing existing was restructured. One shape
change in `createActiveHandler`: the `realRoot === null` case early-returns
`[]` instead of threading a nullable through the closure — TypeScript cannot
narrow a captured `string | null` inside the `files.map` callback, and the
alternative was a `as string` cast. Three response lines duplicated in
exchange for no cast. Deferred: `readArchive` and `createActiveHandler` are
now near-identical (`readdir` → filter `.md` → containment → parse → skip on
throw); extracting a shared reader would cross the `archiveCache` ↔ `devApi`
boundary and is not required by Acceptance, so it is logged, not done.

**The fix.**

- `viz/src/fsSafe.ts` (+30) — `safeRealpath(path)` and
  `realpathWithin(realBase, path)`. Containment is a `sep`-aware prefix test,
  so a sibling like `/base-other` is correctly rejected (it string-prefixes
  `/base` but is not inside it).
- `viz/src/workspace.ts` (+14) — `discoverProjects` resolves the project root
  first, then requires `.flowtron/PLAN.md` to resolve inside it before the
  existing `isFile` check. `readFlowtronVersion`'s `.flowtron/core/SPEC.md`
  read stays deliberately outside containment (comment records why).
- `viz/src/archiveCache.ts` (+15) — `readArchive` resolves `project.root`
  once, then containment-checks every archive `.md` before `readFile`.
  Returns `[]` when the root itself does not resolve.
- `viz/src/devApi.ts` (+17) — `createActiveHandler` gets the same treatment
  (scope widening approved at the 🛠️ gate).

**Base choice.** Containment is anchored on the **project root**, not the
archive/tasknote dir. Anchoring on the leaf dir would be vacuous: if
`archive/` is itself the symlink, everything under its target is trivially
"inside" it. The root is the only bound that catches a symlinked ancestor.

**What this does not change.** Descriptor fields (`root`, `planPath`,
`tasknoteDir`, `archiveDir`) keep their un-resolved values, and
`parseTasknote` still receives the un-resolved display path — so the UI, the
watch sets, and the archive-cache invalidation keys are untouched. Only the
path handed to `readFile` is the resolved one.

**Final Summary:**

The viz dev server can no longer be tricked into reading a file from outside
a project by a symlink. `discoverProjects`, `archiveCache.readArchive`, and
`/api/active` now resolve every candidate file through symlinks and drop it
unless it lands inside that project's own resolved root — while project roots
that are themselves symlinks keep working, which the fleet depends on.
