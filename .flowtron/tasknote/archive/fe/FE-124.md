**Discovery Notes:**

- **Data model (already exists, read-only for this task):** `Task.blockedBy: string[]` is parsed in `viz/src/parser.ts` from PLAN.md `Blocked by [[ID]]` text; `Tasknote.frontmatter.blockedBy?: string[]` comes from tasknote YAML `blocked-by:` (`viz/src/tasknote.ts:14,106,118`). Currently only rendered as a chip (`TaskRowInner.tsx:86`, `RelatedChip ids={task.blockedBy} glyph="⊘" tone="rose"`) — no closure-aware filtering exists yet.
- **Precedent for the filter architecture:** `matchesFilter(task, tasknotesById, query, statusFilter)` in `taskView.ts` is the single pure predicate `pruneMatchingNodes` uses for row visibility today (text query + `TasknoteStatus` set). It is directly unit-tested with fixed positional args in `taskView.test.ts`.
- **`statusFilter` is deliberately half-built, not a pattern to imitate as-is.** Archive-skim probe (CORE-098.5, `archive/core/CORE-098.5.md:23`) found the header "Status filter UI" (`<pills>`) was explicitly removed "per user direction," keeping only the bare `Set<TasknoteStatus>` state so `useKeyboardNav`'s Escape-to-clear still has something to clear (`App.tsx:78` still discards the `toggle` callback: `const [statusFilter, , setStatusFilter] = useToggleSet<TasknoteStatus>();`). This is still true at HEAD. Since the PLAN.md line for FE-124 explicitly asks for a *working* Ready filter (not a repeat of the removed status-filter UI), I'm adding a real toggle control for it rather than leaving state unwired — the CORE-098.5 removal was about that specific status-pills UI, not a standing ban on filter toggles in general.
- **Established shape for a new filter toggle** (epic FE-94.x, e.g. `FE-94.5`/`FE-94.6`): pure selector logic lives in `taskView.ts` with its own `taskView.test.ts` unit tests; a new toggle is a small two-prop presentational component beside `AppHeader.tsx` (pattern: `ViewModeToggle.tsx`, `aria-pressed`) composed into `AppHeader`'s explicit props contract; state stays a plain `useState` in `App.tsx` alongside the existing `query`/`statusFilter` (this is ephemeral filter state, not a persisted display pref like `density`/`palette` in `useViewPrefs.ts`, and not board-selection state like `useBoardSelection.ts`).
- **Design decision — keep `isReady` out of `matchesFilter`.** Rather than growing `matchesFilter`'s signature/responsibility, `isReady(task, tasksById, tasknotesById)` is a sibling pure function, ANDed with the existing `matchesFilter` result at the `App.tsx` call site. Keeps `matchesFilter`'s existing 4-arg contract and its tests untouched (SRP; composition over coupling).
- **`blockedBy` is treated as its own relationship type codebase-wide**, distinct from `relatedTasks` (FE-012 deliberately excluded `blockedBy` from generic back-refs "keeping back-refs to general references only preserves chip semantics — one chip = one relationship type"). Reading `blockedBy` for readiness is consistent with that boundary, not a new one.
- No `SPEC` contract or `PLAN.md` line contradicts this plan; no drift found.

**No clarifications needed (--fast).** Explicit assumptions:
1. "Ready" = the row is open (`!task.completed`) **and** every ID in the union of `task.blockedBy` (PLAN.md) and the tasknote's frontmatter `blocked-by:` is itself closed (`effectiveStatus === 'completed'`). A task with no blockers at all is vacuously ready.
2. An unresolved/dangling blocker ID (not found in the project's task set) counts as **not** ready — we can't confirm closure of something we can't find, and silently ignoring it would be a false "ready."
3. The toggle is plain ephemeral `useState` in `App.tsx` (like `query`/`statusFilter`), not persisted via `useViewPrefs.ts` — consistent with the existing filter state, and Escape clears it along with `query`/`statusFilter`.
