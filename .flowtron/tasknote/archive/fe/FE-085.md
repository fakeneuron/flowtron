**Discovery Notes:**

- Hang path: `gray-matter@4.0.3` `lib/engines.js` binds `yaml.safeLoad` (DEFAULT_SAFE_SCHEMA). That schema registers `!!omap`. js-yaml 3.15.0 `resolveYamlOmap` does `objectKeys.indexOf(pairKey)` per entry → O(n²) CPU, synchronous, blocks the Node event loop. `parseTasknote` is invoked from the viz dev-server (`devApi.ts`, `archiveCache.ts`) on every tasknote file; a crafted note in an adopter checkout (or a malicious archive file) stalls the whole process. Both call sites already `try/catch` and skip on throw (FE-029), so rejecting the tag is the same failure mode as malformed YAML.
- CVE citation: CVE-2026-59870 / GHSA-724g-mxrg-4qvm is the 5.x `YAML11_SCHEMA` `!!omap` issue (5.0.0–5.2.0, fixed 5.2.1). GHSA-5p4m-2wfm-xmqj documents the same weakness on 3.x (3.15.0) and 4.x (4.3.0) where `!!omap` is in the *default* schema — no opt-in required. 3.15.1 exists and switches the uniqueness check to an object-as-set (O(n)), but the PLAN's specified fix is the engine override, which is stronger: CORE_SCHEMA never resolves the tag. 4.x default schema is also affected, so bumping to js-yaml 4 without a schema restriction would not close the hang.
- Fix shape: extend FE-071's `matter(text, { engines: { javascript: … } })` with `yaml: parseYamlFrontmatter` using `yaml.load(input, { schema: yaml.CORE_SCHEMA })`. CORE_SCHEMA ≡ JSON_SCHEMA in js-yaml (str/seq/map + null/bool/int/float) — everything tasknote frontmatter uses. Unknown tags (`!!omap`, `!!js/function`, merge `<<`) throw. `yml` aliases to `yaml` via gray-matter `aliase()`, so one override covers both fence names.
- CORE-233 (2026-05-30): gray-matter latest still 4.0.3; v5 unshipped. Waiting on upstream is the path this task exists to avoid.
- Probe skipped: read set is one call site + the two already-known callers + the two node_modules files named above.
