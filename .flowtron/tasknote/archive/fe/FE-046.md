## 🎯 Goal

Guard against a stale project fetch overwriting the current selection in `useProjectData.load`: re-check `activeProjectRef.current === project` before `setTasks`/`setTasknotesById`.

## ⚡ Notes

Directly matches the filed Low finding from 2026-06-01 audit (Finding #2). No design tradeoffs, obvious shape, under 30min. Fits micro carve-out exactly; no re-scope or promotion to `/ft-task` needed.

The triggering useEffect (:47-50) and refresh path (:52-55) already use the ref for the non-stale case. Zero drift; the described "re-check ... before setTasks/setTasknotesById" is not yet present.

**Archive skim:** `ls _project/tasknote/archive/frontend/` (FE-001 through FE-044 present; no FE-045/046 yet) + targeted `grep -l` for `useProjectData|activeProjectRef|load\(|setTasks|setTasknotesById|project switch|handleSelectProject` across archive/frontend/*.md.

Extending it with the exact guard the PLAN describes is the natural, consistent next step — no new abstraction or API change required.

**Implementation:** One-line guard in the success path of `load()` (viz/src/ui/useProjectData.ts:36-38): after the three parallel fetches + text/json parse, re-check `activeProjectRef.current !== project` and `return` early (before the two `set*` calls) when a stale response arrives. The `finally { setLoading(false) }` still executes (standard for the loader). No other files touched; no new tests (the existing "partial failure on project switch" describe in App.test.tsx plus the reset() path in handleSelectProject already exercise the switch surface; the guard is a silent no-op on happy single-project flows). Decision: minimal per PLAN wording; leverages the ref already present for refresh().

**Docs touched:** no change (the edit is confined to `viz/src/ui/useProjectData.ts`, which is not among the 11 AI-referenced docs in `_project/tasknote/README.md` §"AI-referenced docs"; those are high-level contract/readme surfaces only).
