**Discovery Notes:**

**Version evidence (2026-08-22, `npm --prefix viz outdated`).** In scope: `tailwindcss` 3.4.19 → 4.3.3. `@tailwindcss/vite@4.3.3` peers `vite: ^5.2.0 || ^6 || ^7 || ^8`, so [[FE-090.3]]'s Vite 8 is supported — the two children compose rather than collide. Out of scope and untouched: the unclaimed majors `@types/node` 26, `globals` 17, `js-yaml` 5, `typescript` 7, `@testing-library/jest-dom` 7.

**Tailwind 4 is a config-model change, not a version bump.** There is no `tailwind.config.ts` in the v4 model: `content` globs are replaced by automatic source detection, `darkMode: 'class'` by a `@custom-variant` declaration in CSS, `theme.extend` by `@theme` CSS variables, and the `@tailwind` directives by a single `@import "tailwindcss"`. viz's config is unusually easy to retire — `content` + `darkMode` are its only two live settings, `theme.extend` is `{}` and `plugins` is `[]` (unchanged since [[FE-001]] ported it from legacy, per [[FE-009]]'s drift check). Autoprefixer becomes redundant because v4 prefixes through Lightning CSS.

**Breaking-change sweep over `viz/src` + `index.html` — four renames, one preflight restore, everything else inert.**

*Renames needed (would otherwise silently restyle):*
- `shadow-sm` ×8 → `shadow-xs`. v4 shifted the shadow scale down a step, so a left-alone `shadow-sm` renders as v3's heavier `shadow`.
- `rounded-sm` ×1 → `rounded-xs`. Same one-step shift — 0.125rem would become 0.25rem.
- `focus:outline-none` ×14 → `focus:outline-hidden`. v4 reassigned `outline-none` to `outline-style: none`; `outline-hidden` is the new name for v3's behavior. Same rendering in normal browsers, differs under forced-colors.
- `focus:ring-inset` ×1 (`PrioritySection.tsx:33`) → `focus:inset-ring`. Renamed and reordered in v4.

*Inert — verified, not assumed:*
- **Default border color** (`gray-200` → `currentColor`): every border site carries an explicit color. The only bare `border` is `PrioritySection.tsx:28`, and its companion color always arrives via `palette.SECTION_TINT[priority]` (all 5 entries in each of the 3 palettes in `constants.ts` carry `border-<color>-<n>` + a `dark:` pair). The four `border-t`, two `border-l`, two `border-b`, and one `border-2` site are each colored inline. `border-collapse` is a table utility, unaffected.
- **Default ring color** (`blue-500` → `currentColor`) **and bare-`ring` width** (3px → 1px): zero bare `ring` tokens, and grepping every `ring-<n>` class string for one lacking a companion `ring-<color>` returns nothing — all 15 static rings and all 14 `focus:ring-2` sites are explicitly colored.
- No `space-*` or `divide-*` utilities (so v4's selector change is vacuous), no `@apply` (so no `@reference` needed in any separate file), no `theme()` calls, no `*-opacity-*` utilities, no `decoration-slice`, no `flex-shrink-*` / `flex-grow-*`, no `overflow-ellipsis`, no `drop-shadow`, no `ring-offset`.
- **No test asserts on a class name.** Grepping `toHaveClass` / class-string containment across the 22 test files returns nothing, so the rename cannot move the 391-test baseline. Conversely, that means the test suite gives this task *no* regression coverage — the browser check in Phase 3 is the real verification, not the suite.

*Preflight restore (the one behavior change that isn't a rename):*
- v4's preflight sets `cursor: default` on buttons to match native behavior. viz has **14 `<button>` elements** across 10 components and **zero `cursor-pointer` classes** — it has relied on the v3 preflight this whole time. Left alone, every clickable control in the viz stops showing a pointer on hover. The operator chose to restore it with a `@layer base` rule rather than absorb the regression.
- v4's preflight also resets `<dialog>` margins. `SettingsModal` and `ShortcutsModal` both use native `<dialog>` (via `useDialog.ts`), so centering needs a visual check — assertions in `App.test.tsx` cover `dialog.open`, not layout.
- Light-mode placeholder color shifts (v3 `gray-400` → v4 `currentColor` at 50%). One input, `App.tsx:394`, which sets `dark:placeholder:text-slate-500` but no light-mode placeholder color. Cosmetic and minor; noting it so a light-mode diff isn't mistaken for a regression.

**Open question deliberately left for Phase 2: bare `rounded` (42 sites).** The v4 upgrade-guide rename table lists `rounded-sm`→`rounded-xs` and `rounded`→`rounded-sm`, which implies the bare name was retired — but the v4 border-radius docs still list `rounded` at 0.25rem. The two readings disagree, and guessing wrong silently changes 42 sites. Resolving it by inspecting the built CSS after install is cheap and certain, so the subtask list defers it rather than pre-committing. This is also why the plan diffs built CSS against the baseline rather than trusting the rename list.

It enabled `darkMode: 'class'`, added the synchronous pre-React `theme-init.js` that stamps `.dark` on `<html>` before first paint, and threaded `dark:` variants through 16 components plus the `STATUS_BADGE` / `PRIORITY_BADGE` / `SECTION_TINT` tables. v4 has no `darkMode` key at all, so **re-declaring the dark variant in CSS is the single highest-risk item in this task**: get the `@custom-variant` selector wrong and every one of those variants silently stops matching, with no test to catch it.

**Implementation Notes:**

**Dependency + config swap.** `tailwindcss` 3.4.19 → 4.3.3, `@tailwindcss/vite@4.3.3` added, `autoprefixer` and `postcss` removed from `package.json`. `viz/postcss.config.cjs` and `viz/tailwind.config.ts` deleted — both were straight ports from legacy ([[FE-001]]) that had never carried a project-specific setting beyond `content` and `darkMode`. `postcss` remains in the lockfile as a Vite 8 transitive, which is expected: viz no longer *configures* PostCSS, it just no longer needs to. `@tailwindcss/vite` registered in the plugin array between `react()` and `flowtronApi()`.

**`styles.css` is now the config surface** — `@import 'tailwindcss'`, the `@custom-variant dark (&:where(.dark, .dark *))` declaration replacing [[FE-009]]'s `darkMode: 'class'`, the pre-existing `height: 100%` rule, and a `@layer base` button-cursor rule.

**Two Discovery predictions were wrong, and the built CSS is what caught them.** The plan deliberately deferred both to empirical check rather than trusting the v4 upgrade-guide rename table — that paid off twice:

| Utility | Upgrade-guide table implies | v4 actually emits | Action |
|---|---|---|---|
| bare `rounded` ×42 | renamed to `rounded-sm` | `border-radius:.25rem` — identical to v3 | **left alone** |
| `focus:ring-inset` ×1 | renamed to `inset-ring` | `--tw-ring-inset:inset`, consumed by `ring-2`'s `var(--tw-ring-inset,)` — identical mechanism to v3 | **left alone** |

The `ring-inset` case is the sharper of the two: renaming it to `focus:inset-ring` would have *broken* the fidelity mandate rather than served it. `inset-ring-*` in v4 is a separate utility on its own `--tw-inset-ring-shadow` channel, not a modifier — so `focus:ring-2 focus:inset-ring` would have rendered a 1px inset ring *plus* a non-inset 2px ring, where the v3 pair renders one inset 2px ring. Renaming on the strength of the table would have shipped a visual regression inside a task whose whole point was preserving appearance.

**Three renames applied and verified equal to v3, value-for-value:**

| Rename | Sites | v3 value | v4 emitted | Equal |
|---|---|---|---|---|
| `shadow-sm` → `shadow-xs` | 8 | `0 1px 2px 0 rgb(0 0 0/.05)` | `0 1px 2px 0 #0000000d` | ✅ |
| `rounded-sm` → `rounded-xs` | 1 | `.125rem` | `--radius-xs:.125rem` | ✅ |
| `outline-none` → `outline-hidden` | 14 | `outline:2px solid transparent; outline-offset:2px` | `outline-style:none` + the same `outline:2px solid #0000; outline-offset:2px` under forced-colors | ✅ |

Left untouched because v4 emits v3's exact value: `shadow-xl` (2), `rounded-lg` (4), `rounded-l`/`rounded-r` (6), `rounded-full` (4, `2147483647px` vs `9999px` — functionally identical), and all 29 explicitly-colored `ring-*` sites.

**BSD `sed` silently no-ops on `\b`.** The first rename pass reported success and changed nothing — macOS `sed` does not support GNU word boundaries. Caught by re-grepping for the old names instead of trusting the exit code; redone with `perl` and `(?<![\w-])` lookarounds. Post-rename counts match Discovery's predicted 8 / 1 / 14 exactly.

**Source detection verified, not assumed.** v4 replaces `content` globs with automatic detection, and the highest-consequence unknown was whether it reaches literal class names inside a `.ts` file — `constants.ts` holds the `SECTION_TINT` / `ROW_SELECTION` / `PHASE_DOT` tables that three palettes depend on. Extracted all 364 candidate class tokens from every non-test string literal in `src/` + `index.html` and checked each against the built CSS: **329 present, 35 absent — and all 35 are non-Tailwind strings** (MIME types, module specifiers, DOM ids, `localStorage` keys, YAML field names) with one exception, the pre-existing dead `prose prose-sm` noted above. Arbitrary variants survive too: `[&_p]:my-1` compiles to `.\[\&_p\]\:my-1 p{margin-block:var(--spacing)}`.

**Bundle effect.** CSS grew 29.91 kB → 40.17 kB (5.88 → 7.99 kB gzip). This is v4's `@theme` block — the full default design-token set emitted as CSS custom properties — not extra utilities. JS is unchanged at 244.07/157.11 kB and the module count holds at 306.

**Check 13 is the one real regression this migration introduced, and only the browser caught it.** Both modals rendered pinned to the top-left corner. Cause: Tailwind 4's preflight opens with `*,::after,::before,::backdrop{box-sizing:border-box;border:0 solid;margin:0;padding:0}` — a **universal** margin reset, where Tailwind 3 reset margins only on a named element list (headings, `p`, `blockquote`, `dl`/`dd`, `figure`, `hr`, `pre`). `<dialog>` was never on that list, so v3 left the UA's `margin: auto` intact — which is exactly what centers a modal opened via `showModal()`. Neither `SettingsModal` nor `ShortcutsModal` sets a margin; both had relied on the UA rule since they were written. Fixed with a `dialog { margin: auto }` base-layer rule beside the button-cursor restore, then re-verified in-browser.

This is also the sharpest vindication of the Phase 1 call to treat the browser as the verification surface rather than the suite: `App.test.tsx` asserts `dialog.open`, which stayed `true` throughout — the modal was open the whole time, just in the wrong corner. **Final Summary:**

Migrated viz from Tailwind 3 + PostCSS to Tailwind 4.3.3 on the `@tailwindcss/vite` plugin with a CSS-first config, every gate green and the rendered UI visually identical to the Tailwind 3 baseline. This closes the last implementation child of [[FE-EPIC-090]].

Tailwind 4 is a config-model change rather than a version bump, so the migration is mostly *deletion*: `tailwind.config.ts` and `postcss.config.cjs` are both gone, and `autoprefixer` + `postcss` left `package.json` (Lightning CSS prefixes now). `styles.css` absorbed the config in three lines — `@import 'tailwindcss'`, a `@custom-variant dark (&:where(.dark, .dark *))` replacing [[FE-009]]'s `darkMode: 'class'`, and the existing `height: 100%` rule.

**The upgrade guide's rename table was wrong twice for this codebase, and the built CSS is what caught it.** Discovery deliberately deferred both cases to empirical check instead of pre-committing. Bare `rounded` (42 sites) still emits `.25rem` under v4 — identical to v3 — so it was left alone. More consequentially, `focus:ring-inset` still emits `--tw-ring-inset:inset` and composes with `ring-2` exactly as in v3; renaming it to `focus:inset-ring` as the table implies would have rendered a 1px inset ring *plus* a separate non-inset 2px ring, shipping a visual regression inside a task whose entire point was preserving appearance.

**One real regression, found only in the browser.** Both native `<dialog>` modals rendered pinned to the top-left corner. Tailwind 4's preflight opens with a **universal** margin reset (`*,::after,::before,::backdrop{...margin:0...}`); Tailwind 3 reset margins only on a named element list that never included `<dialog>`, so v3 left the UA's `margin: auto` — the thing that centers a `showModal()` dialog — intact. Fixed with a `dialog { margin: auto }` base-layer rule. `App.test.tsx` asserts `dialog.open`, which stayed `true` the whole time: the modal was open, just in the wrong corner. Nothing in 391 passing tests would ever have caught it.
