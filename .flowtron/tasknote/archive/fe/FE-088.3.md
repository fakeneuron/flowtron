# FE-088.3 | SSE disconnect visibility

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[FE-EPIC-088]] · [[FE-088.2]] · [[FE-011]] · [[FE-064]] · [[FE-062]]

## 🎯 Goal

Make viz's live-update stream failures visible to the user — surface a "live
updates disconnected" state and fall back to polling when the SSE endpoint
returns 503 or the stream closes — instead of silently showing stale data.

## ✅ Acceptance

- [x] `useProjectData` exposes a live-connection state: an SSE `error` marks the stream disconnected, an `open` clears it
- [x] While disconnected the hook polls `refresh()` on a fixed interval, so the board keeps updating instead of going silently stale
- [x] While disconnected with the `EventSource` permanently `CLOSED` (the 503-capacity / non-`text/event-stream` case, where the browser does **not** auto-reconnect), the hook re-attempts the connection on that same interval; a successful reopen restores live updates and clears the state
- [x] `App` renders an amber "live updates disconnected" header chip **and** a banner below the header while disconnected, matching the existing unparsed / duplicate-epic / near-miss shape; both clear on reconnect
- [x] Newest-rejection stays: `MAX_SSE_CLIENTS` + the 503 are unchanged. Oldest-client eviction is considered and declined with the thrash rationale recorded (see Discovery Notes), so `SECURITY.md`'s "503 SSE-capacity reject" bullet stays accurate
- [x] `MockEventSource` models `readyState` well enough to drive both branches (`CONNECTING` retry vs. `CLOSED` fatal); `useProjectData.test.ts` covers disconnect→poll, `CLOSED`→reconnect attempt, and reopen→clear; `App.test.tsx` covers the chip + banner
- [x] `npm --prefix viz test`, `run typecheck`, `run lint` clean

  Two asked, both confirming the recommended path.

  1. **Eviction vs. rejection** — declined eviction, keeping the 503. Rationale: an
     evicted client's stream ends, its browser auto-reconnects, and that reconnect
     evicts the next-oldest — with 11 clients against 10 slots every client flaps
     indefinitely. A server cannot suppress the evicted client's retry, so the thrash
     is not mitigable from that side. Rejection degrades exactly one tab, and this
     task makes that degradation visible and self-healing. `SECURITY.md` stays
     accurate as a side effect.
  2. **UI loudness** — chip **and** banner, matching the existing unparsed /
     duplicate-epic / near-miss pattern. A chip alone is too quiet for a failure
     whose whole defect is being unnoticeable.

  Assumptions: (a) one 5 s interval serves both the poll refresh and the reconnect
  attempt — no separate cadences, no backoff, since this is a localhost dev tool;
  (b) reconnect is attempted only when the socket is `CLOSED` — while it is
  `CONNECTING` the browser is already retrying and a second socket would race;
  (c) polling continues during `CONNECTING` too, so a slow browser retry does not
  leave the board frozen; (d) no page-visibility gating — three localhost fetches
  every 5 s in a background tab is not worth the extra branch.

**Discovery Notes:**

**Root cause, precisely.** Two distinct failure shapes hide behind one `error`
listener:

| Shape | `readyState` after `error` | Browser retries? | Covered before? |
|---|---|---|---|
| Mid-stream drop (server restart, socket RST) | `CONNECTING` (0) | yes | yes — [[FE-064]] |
| Handshake reject (503 capacity, wrong content-type) | `CLOSED` (2) | **no** | **no** |

The second row is Finding #5: the tab is permanently dead, the board is frozen, and
nothing on screen says so. Distinguishing them needs `readyState`, which the current
listener never reads.

**Design.** `useProjectData` keeps the `EventSource` in a ref behind a `connect()`
closure. `error` sets `liveDisconnected` and starts one 5 s interval; each tick calls
`refresh()` (the poll fallback, covering both rows) and, when the socket is `CLOSED`,
calls `connect()` again (recovery, covering the second row — a slot may free up).
`open` clears the flag, stops the interval, and keeps [[FE-064]]'s `droppedSinceOpen`
reconcile untouched. `App` gates an amber chip and an amber banner on the returned
flag.

**Deferred cleanup.** The amber banner block in `App.tsx` will have four near-identical
instances after this change. Extracting a `<WarningBanner>` is a reasonable follow-up
but is not required by Acceptance and would touch three unrelated render paths — left
alone per the Minimal Refactor Gate.

**Gate judgment:** Discovery surfaced no significant deviation — both asks confirmed
the planned approach, the file set is unchanged, and the subtask list did not
restructure → skip 🛠️.

**Final Summary:**

Viz no longer freezes silently when its live-update stream dies. The board now says so
on screen, keeps refreshing by poll while it is down, and reconnects on its own when
the stream becomes available again — with no page reload.

The bug had a specific shape worth recording. Two very different failures arrived on
one `error` listener: a mid-stream drop, after which the browser retries by itself
(handled since [[FE-064]]), and a **rejected handshake** — [[FE-062]]'s 503 once
`MAX_SSE_CLIENTS` is full, or any non-`text/event-stream` response — after which the
browser fails the connection outright and never retries. The client treated both as
the first case: it set `droppedSinceOpen` and waited for an `open` that, in the second
case, could never arrive. That tab's board stayed frozen indefinitely with nothing on
screen to say so. Telling the two apart requires `readyState`, which the old listener
never read.
