# FE-101.5 | archive-cache-bound

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[FE-EPIC-101]] · [[FE-101.2]] · [[FE-101.4]]

## 🎯 Goal

Cap `archiveCache`'s per-project `Tasknote[]` retention with an LRU eviction policy (5 projects) so fleet-wide memory cost is bounded by structure, not by how many projects a session happens to visit.

## ✅ Acceptance

- [x] `archiveCache.ts` evicts the least-recently-used project's cache entry once more than `MAX_CACHED_PROJECTS` (5) distinct projects are held, so the map never grows past that bound regardless of how many projects a session visits.
- [x] A `get()` call on an already-cached project counts as a "use" — it moves that project to the most-recently-used position, so repeatedly viewing the same handful of projects never evicts them.
- [x] Existing `invalidate()` / `invalidateProject()` / `clear()` behavior and cache-hit/miss semantics (including the in-flight-promise dedup and error-clears-cache-entry behavior) are unchanged.
- [x] New tests cover: eviction fires once the cap is exceeded (oldest goes first), and touching a cached project via `get()` protects it from being the next eviction.
- [x] `npm --prefix viz test`, `npm --prefix viz run typecheck`, and `npm --prefix viz run lint` all clean.

## 🧩 Subtasks

- [ ] `archiveCache.ts`: add `MAX_CACHED_PROJECTS = 5` module constant (precedent: `devApi.ts`'s `MAX_SSE_CLIENTS`).
- [ ] `archiveCache.ts`: on a cache hit in `get()`, re-insert the entry (`delete` + `set`) to move it to the Map's most-recently-used tail before returning it.
- [ ] `archiveCache.ts`: after inserting a new entry in `get()`, if `cache.size > MAX_CACHED_PROJECTS`, delete the oldest key (`cache.keys().next().value`).
- [ ] `archiveCache.test.ts`: add an eviction test (populate 6 distinct projects, assert the 1st is evicted — next `get()` re-reads rather than returning the cached promise).
- [ ] `archiveCache.test.ts`: add a touch-protects-from-eviction test (re-`get()` project A after populating others, then push past the cap — A survives, the next-oldest untouched project is evicted instead).
- [ ] Run `npm --prefix viz test`, `run typecheck`, `run lint`.

**Discovery Notes:**

**Fleet-wide sizing math (workstation survey, 2026-08-29).** `find ~/code/*/.flowtron/tasknote/archive -name '*.md'` across the 23 flowtron-adopted projects on this machine: 6,445 archived notes total, 106.9MB raw markdown (`du -sk`) across per-project archive dirs ranging from 3 notes/32KB (`fakeneuron-nas`) to 1,531 notes/30.9MB (`marscharts`). Applying FE-101.2's measured 83.9% in-memory-retention reduction (1,771,547 / 10,976,000 bytes on flowtron's own 795-note archive) as a flat ratio across the fleet gives an estimated **~17.2MB** worst-case total if a single dev-server session's cache held every project's archive at once (today: unbounded map, one entry per project ever `get()`'d since last restart or invalidation). This is an estimate — actual in-memory `Tasknote[]` object overhead differs from JSON-wire byte counts — but the order of magnitude is what mattered for the Relevance Assessment, not the exact figure.

**Why a cap still matters at ~17MB.** The number is small in absolute terms for a local dev tool, but the epic's stated goal is "bound the cost by structure instead of archive size" — a 5-project LRU cap is architecturally cheap (one constant + two `Map` operations, no new dependency) and keeps the ceiling fixed as the fleet keeps growing, rather than the ceiling being "small today, and growing 1-2 projects/month indefinitely."

**How the cap interacts with existing eviction paths.** `invalidate()` (per-file change) and `invalidateProject()` (tasknote unlink) already delete individual entries outside of any LRU logic — the new cap is a third, independent eviction trigger (size-based) layered on the same `Map.delete()` primitive, not a replacement for the other two. `clear()` (server shutdown) is unaffected.

## 🛠️ Phase 2: Execution

- [x] **Pattern survey** — followed `devApi.ts`'s `MAX_SSE_CLIENTS` precedent for a module-level bound constant guarding an unbounded collection. No existing LRU implementation anywhere in `viz/src` to extend; used the `Map`'s native insertion-order iteration (delete+reinsert to touch, `keys().next().value` to find the oldest) rather than adding a dependency or a parallel bookkeeping structure — the cache was already a `Map`, so this is the minimal-diff shape.

- [x] **Minimal refactor gate** — no refactor beyond the two `get()` branches (touch-on-hit, evict-on-insert-when-over-cap) and the one new constant. `invalidate()` / `invalidateProject()` / `clear()` are untouched — they already express "delete this project's entry" and the LRU logic reuses that same primitive without needing to change them.

- [x] Implemented the minimal solution

- [x] Updated/added tests for non-trivial behavior — 2 new cases (eviction-at-cap, touch-protects-from-eviction)

**Implementation Notes:**

`viz/src/archiveCache.ts` (+13/−4):

- Added `const MAX_CACHED_PROJECTS = 5;` above `createArchiveCache`.
- `get()`'s cache-hit branch now does `cache.delete(project.name); cache.set(project.name, cached);` before returning — a `Map` re-insert moves the key to the end of iteration order, marking it most-recently-used.
- `get()`'s cache-miss branch, after `cache.set(project.name, cached)`, adds: if `cache.size > MAX_CACHED_PROJECTS`, delete `cache.keys().next().value` (the oldest surviving key, since JS `Map` iterates in insertion order and every hit re-inserts).
- The in-flight-promise dedup (two concurrent misses returning the same promise) and the error-clears-cache-entry `.catch` are unchanged — the `.catch` still closes over the same `cached` variable it always did, comparing `cache.get(project.name) === cached` before deleting on rejection, which stays correct because eviction never removes an entry that is still `===` the promise a concurrent caller is holding without also having genuinely deleted it from the map.
