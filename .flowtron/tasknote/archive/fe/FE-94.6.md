**Decisions carried forward from the starter (locked at filing, re-affirmed
here).**

| Decision | Choice | Rationale |
|---|---|---|
| Two hooks, not one | prefs vs selection | Different lifetimes and different inputs; prefs key on `activeProject`, selection keys on `tasks` |
| Reset lives with the state | `resetForProjectSwitch()` on `useBoardSelection` | `handleSelectProject`'s six-way fan-out is the exact thing that drifts when state and reset are separated |
| Position in sequence | Last | Highest risk; lands on a file already thinned and fully pinned |
| No reducer | Keep `useState` / `useToggleSet` | Matches the codebase's existing idiom; a reducer would be a rewrite, not a move |

**The `rowInteraction` identity surface.** Its memo deps span both hooks plus
`tasknotesById`. Because the hooks return the same `useState`/`useToggleSet`
setters and the same `useCallback`-stable `navigateToTask`, every dep keeps its
current identity and the memo re-renders on exactly the same transitions as
today. The row/subtask expand-toggle, highlight, and navigation tests are the
guard.

**Explicitly out of scope.** `useProjectData` / `useProjects` (already
extracted, untouched) · `useKeyboardNav` (stays wired in `App` with the same
params object) · introducing a reducer, store, or new context for this state ·
changing highlight duration, rAF sequencing, or scroll behavior · any cleanup
in `App.tsx` beyond what this move makes unused.
