# FE-98 | derive-registries-single-source

[← PLAN.md](../PLAN.md) · 🟢 In progress

## 🎯 Goal

Collapse three duplicated key registries in `viz/` to a single source each —
parser section headings, palette/density preference keys, and starter
subsection keys — so adding a value in one place cannot silently desync a
consumer.

## ✅ Acceptance

- [x] `viz/src/parser.ts` exports one ordered `PRIORITIES` registry; `SECTION_HEADINGS` is derived from it and stays file-local (no second export).
- [x] `App.tsx` no longer hand-lists priority names: `SECTIONS` is `PRIORITIES`, and `BELOW_BOARD_SECTIONS` is derived by subtracting `BOARD_SECTIONS` (the one remaining hand-authored *layout* declaration).
- [x] `viz/src/visibilityPrefs.ts` owns `DENSITY_MODES` / `PALETTE_NAMES` as the single source: the `DensityMode` / `PaletteName` types and the `isDensity` / `isPalette` guards are all derived from those arrays.
- [x] `SettingsModal.tsx` declares no local key arrays — `DENSITY_KEYS`, `PALETTE_KEYS`, and `STARTER_SECTION_KEYS` are gone, replaced by imports of `DENSITY_MODES`, `PALETTE_NAMES`, and the existing `STARTER_SUBSECTION_KEYS`.
- [x] Adding or renaming a member of any of the four registries is a compile error or a single-file edit — never a silent desync between producer and consumer.
- [x] Targeted tests + typecheck + lint green; the Settings modal renders the same radios/checkboxes as before (no user-visible change) — operator-confirmed at `localhost:5120`, 2026-08-26.

## 🧩 Subtasks

- [x] `parser.ts`: add exported `PRIORITIES: readonly Priority[]`; rewrite `SECTION_HEADINGS` as `new Set<Priority>(PRIORITIES)`.
- [x] `taskView.ts`: widen the `sections:` params of `emptySections` / `collectVisibleIds` to `readonly Priority[]` so the readonly registry is accepted.
- [x] `App.tsx`: import `PRIORITIES`; `SECTIONS = PRIORITIES`; derive `BELOW_BOARD_SECTIONS` by subtraction; drop the two literal lists.
- [x] `visibilityPrefs.ts`: add `DENSITY_MODES` / `PALETTE_NAMES` const arrays; derive both types via `(typeof X)[number]`; derive `isDensity` / `isPalette` via `.includes`.
- [x] `SettingsModal.tsx`: import the three registries; delete `DENSITY_KEYS`, `PALETTE_KEYS`, `STARTER_SECTION_KEYS`; `StarterSectionKey` **kept** — still the `setStarterSection` param type, and its structural identity with `StarterSubsectionKey` is what makes future divergence a compile error.
- [x] Add targeted tests pinning the derivation (guards accept every array member; `PRIORITIES` covers the rendered section set).
- [x] Run `viz` typecheck + lint + targeted vitest — plus the full suite, since `parser.ts` + `App.tsx` are broad.

### Best Practices Review

- **Responsibilities.** `parser.ts` owns the `Priority` domain (type + heading set) — it should own the ordered registry too. `App.tsx` owns *layout* (which priorities render as board columns) — that stays hand-authored and local. `visibilityPrefs.ts` owns the pref vocabulary; `SettingsModal.tsx` is a pure renderer and should own **no** registries.
- **Dependency direction.** All four fixes point `ui/ → src/`, the direction already in use (`App.tsx:2` imports `groupTasks` from `../parser`; `TaskDetail.tsx:4` imports from `../tasknote`; `constants.ts:1-3` imports from all three). No new edge; no cycle; nothing crosses the FE-97 "no Node under `src/ui/`" rule.
- **Existing abstraction to extend.** `parser.ts:299-301` already derives `LOWERCASE_TO_PRIORITY` from `SECTION_HEADINGS` (CORE-425.3) — deriving a second consumer from one registry is the established shape here, not a new one. `constants.ts:75-76` (`Record<Priority, string>`) is the in-repo precedent for compile-checked exhaustiveness.
- **Public-surface budget.** [[FE-100]] is already filed to *de-export* nine file-local symbols, so this task adds the minimum: **three** new exports total (`PRIORITIES`, `DENSITY_MODES`, `PALETTE_NAMES`) while removing four hand-maintained lists. `SECTION_HEADINGS` deliberately stays file-local — exporting the `Set` as the PLAN line's literal wording suggests would add a fourth export that only `parser.ts` ever reads.
- **Deferred (out of scope).** `visibilityPrefs.ts:70-97` `parsePrefs` still spells out each `rowChips` / `detailSections` / `starterSections` field by hand. Deriving those from key arrays is a larger rewrite of validated-parse logic with no drift risk today (the fields are compile-checked against `VisibilityPrefs`), and the PLAN line does not name it. Left alone.
- **Non-duplication confirmed.** `taskView.ts:51` `groupBySection` builds its `Record<Priority, …>` via `groupBy` + `?? []` at every read site — no hand-listed registry there. `constants.ts` `SECTION_TINT` / `PRIORITY_BADGE` are already exhaustive `Record<Priority, …>` and compile-checked.
