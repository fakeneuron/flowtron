**Discovery Notes:**

Root cause is display grouping, not the parser. `parsePlanWithDiagnostics` already sets both `priority` (from `##` heading) and `completed` (from `[x]`). `App.tsx` `bySection` groups solely by `n.task.priority`, so the checkbox never moves a row. `effectiveStatus` already treats the PLAN.md checkbox as authoritative for status chips/filters; display grouping should follow the same overlay.

SPEC/tasknote-selection.md §"`## Completed` archive convention" is a PLAN.md *placement* rule (standalone → top of `## Completed`; epic child stays nested under the active parent until `/ft-close-epic`). It does not forbid the viz from showing a top-level `[x]` in Completed when the heading hasn't moved yet. It *does* forbid stranding an epic child as its own Completed row — `groupTasks` already nests children, and grouping operates on parent nodes, so children stay put.

`navigateToTask` today expands `target.priority`. After the overlay, a checked standalone under `## Medium` renders in Completed (collapsed by default), so jump-to must expand `displaySection` of the *rendered* node (the parent epic when the id is a child).

Archive skim (`archive/fe/`): FE-044 established the `bySection` post-`groupBy` sort for `[!critical]` — extend that same memo, don't invent a second grouping path. FE-016 / FE-015 established `effectiveStatus` (`task.completed` wins). FE-063.3 / CORE-432.3: both views + counts derive from `filteredNodes` → `bySection`, so one keySelector covers list and board. No prior tasknote decided heading-vs-checkbox for the Completed bucket.
