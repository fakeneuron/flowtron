# FE-101.4 | collapsed-section-unmount

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[FE-EPIC-101]] · [[FE-101.2]] · [[FE-101.3]]

## 🎯 Goal

Stop mounting a collapsed `PrioritySection`'s row subtree (currently kept mounted via CSS-only `grid-rows-[0fr]` collapse) and wrap `TaskRow`/`EpicRow` in `React.memo` so an expanded section's ~780 rows don't re-render on every search keystroke.

## ✅ Acceptance

- [x] `PrioritySection` no longer mounts a collapsed section's row subtree — when `collapsed` is true, `nodes` render no `TaskRow`/`EpicRow` DOM at all (the CSS-only grid-rows collapse-but-stay-mounted trick is replaced with conditional rendering). EpicRow's own subtask-list expand/collapse animation is untouched — this is scoped to PrioritySection's section-level collapse only.
- [x] `TaskRow` is wrapped in `React.memo`.
- [x] `EpicRow` is wrapped in `React.memo`, and its props are stabilized so the memo bail is actually effective (not a no-op wrapper): `pruneMatchingNodes` reuses the original node/children references when filtering removes nothing, and `EpicRow` takes the stable `toggleEpic` function + task id instead of a fresh per-render closure.
- [x] New tests cover: a collapsed `PrioritySection` renders no row DOM; `TaskRow`/`EpicRow` skip re-render when props are unchanged; `pruneMatchingNodes` reuses references when nothing is filtered.
- [x] `npm --prefix viz test`, `npm --prefix viz run typecheck`, and `npm --prefix viz run lint` all clean.
- [x] Visual confirmation: priority-section collapse/expand still works (now instant, no transition) and epic subtask expand/collapse animation is unaffected.

**Discovery Notes:**

**Why `nodes` churns every keystroke regardless of memo.** `App.tsx`'s `filteredNodes` → `bySection` pipeline calls `pruneMatchingNodes(allNodes, matchesFilter)` on every `query` change, which today (`taskView.ts:39-46`) does `n.children.filter(matches)` and returns `[{ task: n.task, children }]` for *every* node unconditionally — even nodes whose matched-children set didn't change. `TaskRow`'s `task` prop survives this unaffected (it's `n.task`, passed through, never reconstructed). `EpicRow`'s `node` prop does not — it's a brand-new object every call. Reusing `n.children` when the filtered length equals the original length, and reusing `n` itself when that reused-children check holds and `n.task` still matches, restores referential stability for the common no-filter-active state and for any query that doesn't touch a given epic's own children.

**Why `toggleExpanded` also breaks memo today.** `PrioritySection.tsx:57` builds `() => toggleEpic(node.task.id)` fresh inside `nodes.map(...)` on every `PrioritySection` render — including a render triggered by toggling a *different* epic (since `expandedEpicIds`/`toggleEpic` come from `useRowInteraction()` context, and `toggleEpic` from `useToggleSet` always produces a new `Set` on toggle). `toggleEpic` itself is `useCallback`-stable (`useToggleSet.ts:8`, `[]` deps), so passing it straight through and letting `EpicRow` build `() => onToggleExpanded(task.id)` internally removes the per-render closure allocation from the unstable prop position entirely.

**A testing technique dead-end, recorded so it isn't retried.** The first attempt at the memo-bail tests used `React.Profiler`'s `onRender` callback, reasoning "no re-render → no commit → no callback." Switched to spying directly on `Component.type` (the function `React.memo` wraps), which counts actual invocations of the render function body — the thing the acceptance criterion is actually about.
