# FE-091 | watch-event iterator fix

[← PLAN.md](../PLAN.md) · 🟢 In progress · 🔗 [[FE-088.3]] · [[FE-090.2]] · [[FE-090.N]]

## 🎯 Goal

Fix `createOnWatchEvent` so it no longer consumes a one-shot `Map` iterator, restoring FE-088.3 SSE attribution and archive-cache invalidation across every watch event, and cover the regression with a test that passes a live iterator rather than an array.

- [x] `createOnWatchEvent` iterates a stable, re-iterable project list — a one-shot iterator passed by the caller no longer dies after the first iteration

- [x] [[FE-088.3]] SSE attribution fires: a `PLAN.md` change broadcasts `data: {"project":"<name>"}`, not `data: {}`
- [x] A regression test constructs the handler with a live `Map.values()` iterator (not an array) and asserts both behaviours across ≥2 events — the case the existing array-based suite is structurally unable to express
- [x] `npm test`, typecheck, and lint clean in `viz/`

**Discovery Notes:**

**Root cause (confirmed, not hypothesised).** `viz/vite.config.ts:80` passes
`projects.values()` — a `Map` iterator, single-pass by spec — into
`createOnWatchEvent`. The returned handler (`viz/src/flowtronWatch.ts:132-146`)
closes over `opts.projects` and iterates it **up to three times per event**
(`archiveCache.invalidate`, `projectForActiveTasknote` on `unlink`,
`projectForPath`) and is reused for **every** event on both watchers. So:

- *Event 1, `PLAN.md` change*: `invalidate()` walks the iterator to exhaustion
  without matching (a `PLAN.md` path is under no `archiveDir`), leaving
  `projectForPath()` a dead iterator → `broadcast.schedule(undefined)` →
  [[FE-088.3]]'s attribution silently never works.
- *Event 2 onward*: the iterator is dead for `invalidate()` too → archive-cache
  invalidation stops matching entirely and stale archive data can be served.

Note `invalidate()` early-returns on its first match, so on an *archive* first
event the iterator is left partially advanced rather than exhausted — the
failure is position-dependent, which is worse than a clean break, not better.

**Read set:** `viz/vite.config.ts`, `viz/src/flowtronWatch.ts`,
`viz/src/watchSet.ts`, `viz/src/archiveCache.ts`,
`viz/src/flowtronWatch.test.ts`. Narrow and known — no probe needed.

**Best Practices Review.** The touched responsibility is a single one:
`createOnWatchEvent` owns *"turn a chokidar event into a cache invalidation +
an attributed broadcast"*. Its dependency direction is already clean (it
consumes `ArchiveCache` / `watchSet` helpers, none of which know about it).
The defect is not a boundary problem — it is a **contract lie**: the signature
advertises `Iterable<ProjectDescriptor>`, which promises nothing about
re-iterability, while the implementation depends on re-iterability. Two honest
resolutions exist (narrow the type, or make the implementation live up to the
signature); see the clarification below. No duplication nearby;
`devApi.ts:69` already materializes with `Array.from(projects.values())`, which
is the same instinct applied correctly and is the local precedent for the
chosen fix. No refactor required beyond the fix itself; no cleanup deferred.

**Clarifying question asked** — the fix shape was a genuine two-way design
choice, so it went to the operator rather than being picked silently:

- **Option A (chosen)** — materialize `opts.projects` once at construction,
  keeping the permissive `Iterable` contract. Makes the implementation honour
  the signature it already advertises, matches the `devApi.ts:69` precedent,
  and is *directly testable*: the regression test can hand in a real
  `map.values()`. This is what [[FE-090.N]] asked for.
- **Option B (declined)** — narrow the parameter to `readonly
  ProjectDescriptor[]` and pass `discovered` at the call site. Stronger
  prevention (a future `.values()` becomes a compile error), but it makes the
  runtime regression test impossible to write without an `as unknown as` cast
  defeating the very type doing the protecting.

**Explicit assumptions** carried into Phase 2: (1) the `projects` Map is fully
populated before `createOnWatchEvent` is constructed and is not mutated
afterwards — verified by reading `configureServer`, where discovery completes
above the watcher block and no later `.set`/`.delete` exists — so a
construction-time snapshot loses no liveness; (2) the call site keeps
`projects.values()`, which is now safe, rather than adding a redundant second
snapshot.

**Implementation Notes:**

**Pattern survey.** `viz/src/devApi.ts:69` already faces the identical problem
and solves it with `Array.from(projects.values())` — materialize before use.
That is the established local shape for "this consumer needs a list, not a
sequence," so this fix extends it rather than inventing one. No new abstraction
introduced; no helper extracted for a two-call-site pattern.

**Minimal refactor gate.** One line of behaviour change plus a comment. The
three call-sites inside the handler were repointed from `opts.projects` to the
materialized `projects` — required by Acceptance, not cleanup. Nothing else in
the file was touched: `WATCH_HOT_OPTIONS`, the `ignored` predicates, and the
broadcaster are all adjacent and all left exactly as [[CORE-431.2]] /
[[FE-090.2]] left them. No cleanup deferred (none found in the touched path).

**The change** (`viz/src/flowtronWatch.ts`, +11/-3): `createOnWatchEvent` now
snapshots its input once at construction —

```ts
const projects = [...opts.projects];
```

— and the per-event body reads that array. The parameter stays
`Iterable<ProjectDescriptor>` deliberately: the signature was never wrong, the
implementation just failed to honour it. Now any iterable a caller passes —
array, `Map.values()`, generator — behaves identically. `vite.config.ts:80` is
left as `projects.values()`; it is correct as written now, and a second
snapshot at the call site would be redundant belt-and-braces.

The comment above the line names the hazard, the symptom, and the assumption
that makes snapshotting safe, so the next reader does not "simplify" it back.

**Final Summary:**

Fixed the one-shot-iterator defect that silently disabled [[FE-088.3]]'s SSE
project attribution and killed archive-cache invalidation after the first watch
event: `createOnWatchEvent` now materializes its `projects` input once at
construction instead of re-walking a `Map.values()` iterator that dies on first
use. Three regression tests pin it by constructing the handler exactly as
production does — with a live `Map.values()` — closing the gap [[FE-090.N]]
identified, where every existing test passed a re-iterable array and the shared
`Iterable` type made the two call sites indistinguishable.

**Changed:** `viz/src/flowtronWatch.ts` (+11/−3 — one materialization line, a
seven-line comment naming the hazard and its safety assumption, three call-sites
repointed) and `viz/src/flowtronWatch.test.ts` (+84 — three tests).

**Verified:** 394 tests pass (up from 391), `tsc --noEmit` clean, `eslint src`
clean. The three new tests were run against a reverted fix and all three failed
— the first with `expected [ undefined ] to deeply equal [ 'alpha' ]`, the exact
`data: {}` symptom — while the 20 pre-existing tests passed in both states. A
live dev-server SSE smoke test fired three sequential events and all three
arrived attributed as `{"project":"flowtron"}`, including the third; before the
fix all three were `data: {}`.

**Refactors:** none beyond the fix. `vite.config.ts:80` deliberately left as
`projects.values()` — now correct, and a second snapshot there would be
redundant. Adjacent watcher options ([[CORE-431.2]], [[CORE-222]]) untouched.
Nothing deferred.

**Design note:** the alternative — narrowing the parameter to `readonly
ProjectDescriptor[]` — offers compile-time prevention but would have made the
runtime regression test unwritable without a cast defeating the type doing the
protecting. The operator chose implementation-honours-signature; the exported
signature is unchanged, so no caller is affected either way.

**Documentation:** no change across all 16 AI-referenced docs.

**Maintainability:** the function now behaves the same for every kind of
iterable, so the production and test call sites can no longer differ in the one
property that mattered — and the suite can finally express the failure mode
that three test-green closures walked past.
