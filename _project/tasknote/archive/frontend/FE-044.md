- **Touch points (12 files):** `viz/src/parser.ts`, `viz/src/ui/App.tsx`, `viz/src/ui/constants.ts`, `viz/src/ui/TaskRowInner.tsx`, `viz/src/ui/EpicRow.tsx`, `viz/src/ui/CriticalChip.tsx` (new), `viz/src/ui/App.test.tsx`, `templates/PLAN.md`, `SPEC.md`, `docs/MIGRATION.md`, `claude/skills/ft-{task,micro-task,epic-discovery,starter-task,file-followup,release,audit}/SKILL.md` (7 skill files — 5 priority-list + 2 release/audit heading scans). `BoardView.tsx`, `PrioritySection.tsx`, `TaskRow.tsx` need no edits.
- **Sort step placement** — cleanest spot is `App.tsx` `bySection` `useMemo` (L193-196) — after the groupBy, wrap with a per-priority post-sort that pulls `critical: true` to the front when `priority === 'High'`. Alternative: do it inside `PrioritySection`, but that couples sort logic to render and breaks for any future "criticals also appear elsewhere" change. Going with the App.tsx approach.
- **Regex extension** — `[!critical]` and `[model]` can appear in either order. To stay tolerant, the simplest scheme is to declare each as an independent optional group after `**TASK-ID**`. Two tokens × 2 orderings = 4 alt branches in a strict regex, OR a single permissive scheme: capture a `[bracket]` sequence and post-process. Going with the **two-group strict-order**: `[!critical]` BEFORE `[model]` (canonical: `**ID** [!critical] [opus] | shortname`). Cheap, predictable, and matches the question preview. Document in SPEC §"Task-line format" with the canonical ordering rule.
- **CRITICAL_FLAG palette tokens** — Default = red (matches the dropped `SECTION_TINT.Critical`); Linear = rose (matches its dropped tint); GitHub = fuchsia (matches its dropped tint). Identity preserved per palette.

**Implementation Notes:**

- **Sort approach** — `App.tsx` `bySection` `useMemo` wraps the existing `groupBy` call: when `grouped.High` exists and has >1 rows, splice in a stable critical-first sort via `Number(b.task.critical) - Number(a.task.critical)`. Stable `Array.prototype.sort` preserves source order within both the flagged and un-flagged groups. Sort applies only to High (other priority columns keep their existing source-order semantics).
- **Regex shape** — strict two-group grammar `[!critical]` BEFORE `[model]`. Tolerating either order would have required 4 alt branches or a post-process pass; the canonical ordering (documented in SPEC + templates/PLAN.md) is cheaper.
- **Legacy heading parser state** — introduced a `legacyCriticalSection` boolean alongside `currentPriority`. Set when the heading text is the literal `'Critical'`; cleared on every other heading. Each task in scope inherits `critical = criticalRaw === '!critical' || legacyCriticalSection`.
- **Palette tokens** — Default = `bg-red-100 text-red-800 …`, Linear = `bg-rose-100 …`, GitHub = `bg-fuchsia-100 …`. Mirrors each palette's dropped `Critical` `PRIORITY_BADGE` color so the visual identity carries over.
- **CriticalChip placement** — first chip in the right cluster (before `StatusChip` + `ModelChip`). High-signal flag deserves leftmost (in LTR reading, rightmost in row). Always-on; no `visibility.rowChips.critical` toggle.

`Critical` is no longer a `Priority` value — it's now an orthogonal per-task flag declared with `[!critical]` on the PLAN.md task line (mirroring the existing `[opus]/[sonnet]` shape).
