**Discovery Notes:**

- **Drift check passes** with one load-bearing finding: `viz/src/tasknote.ts:34-39` `STATUS_VALUES` does NOT include `'starter'`, so today `parseFrontmatter` returns `null` for any tasknote with `status: starter` (line 67 reject). A starter currently renders identically to a "no tasknote" row. Adding `'starter'` to `TasknoteStatus` + `STATUS_VALUES` is the load-bearing first edit; everything else builds on it.
- **Counts come for free:** once `'starter'` parses, the existing `inProgress` filter (`App.tsx:160-168`, `tn.frontmatter.status === 'in-progress'`) naturally excludes starters. The only addition is the new starter-count segment in the subtitle.
- **PhaseDots needs an explicit guard** (always renders when `tn` exists, line 591); `SubtaskProgress` is already self-gated on `subtasksProgress.total > 0` so it stays inert for starters.
- **TaskDetail (lines 756-788)** branches on `tasknote ? <Goal/Acceptance/Subtasks> : <description>`; starters need a third branch. `extractSection(body, 'Starter context')` already works (substring match) — adding a `starterContext` field to `Tasknote` keeps the parsing centralized and the UI declarative.
- **No active starter tasknotes exist** in `_project/tasknote/` (CORE-027 was promoted before closure). Visual confirmation will require a throwaway starter file created during Phase 3 and removed before closure.
- **Clarifying questions** (resolved 2026-05-03 via AskUserQuestion):
  1. Starter on filter rail? → **Yes** — added to `STATUS_FILTER_VALUES`.
  2. Header subtitle counts? → **Add separate starter count** — `N tasks · M in progress · K starters` (only when K > 0).

**Implementation Notes:**

- **Files edited (3):** `viz/src/tasknote.ts` (+3 lines: status union, set entry, interface field, `extractSection` call), `viz/src/ui/App.tsx` (+18 / -6 lines: status maps, filter rail, `starterCount` memo, subtitle copy with pluralization, `PhaseDots` gate, `TaskDetail` starter branch), `viz/src/tasknote.test.ts` (+50 lines for 2 new tests).
- **STATUS_LABEL choice:** put the 🌱 emoji directly into `STATUS_LABEL['starter'] = '🌱 Starter'` so both the header filter-rail chip and the row-level status badge render consistently from a single source. The badge's `uppercase` CSS only affects the word, not the emoji — renders as `🌱 STARTER` on rows and `🌱 Starter` on the filter rail (intentional case difference, mirrors the existing badge pattern).
- **DetailSection vs bare WikilinkMarkdown for starter body:** went with `DetailSection title="🌱 Starter context"` for visual consistency with Goal/Acceptance/Subtasks sections (small uppercase-tracking-wide title above the body). Bare `WikilinkMarkdown` would have rendered the body without a section title, looking jarring next to the standard expand layout.
- **Pluralization:** caught during visual review — initial `${starterCount} starters` rendered as "1 starters". Fixed to `${starterCount} ${starterCount === 1 ? 'starter' : 'starters'}`. The existing "in progress" doesn't pluralize because it's an adjectival phrase, not a noun count.
