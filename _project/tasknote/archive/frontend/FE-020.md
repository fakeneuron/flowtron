### Bugs surfaced (file as new PLAN.md entries — log-only, no inline fix per user lock)

1. **Cold-start 500 on `/api/archive?project=<name>` for some projects.** First request to `bananapeel`, `fintown`, `flowtron` archive endpoints returned 500 ("Archive list failed: HTTP 500" in the UI banner; `Failed to list archived tasknotes: …` on the wire). Retry (page reload or `r` key) succeeds — confirmed via `curl` returning 200 + 3.2MB for fintown after the first failure. Smaller-archive projects (flowtron-nat-011, InvisiPaw, natabula, photard) loaded cleanly first try. Suspected cause: a `parseTasknote` exception on a specific archive file in larger projects propagates through `Promise.all` in `viz/src/archiveCache.ts:readArchive` (lines 16-34). `createArchiveCache.get` deletes the cache entry on failure (line 49-52), so the retry rebuilds — but the retry succeeds, which is itself suspicious (suggests timing-dependent, not deterministic file failure). Worth filing as an investigation task: instrument `readArchive` to log which file fails, then either fix the file or make `Promise.all` tolerant of per-file failures.

2. **Stale-data state when `load()` partial-fails.** In `viz/src/ui/App.tsx:61-83`, `load(project)` does `Promise.all([planRes, activeRes, archiveRes])`, checks each response, and throws on any non-OK before calling `setTasks` / `setTasknotesById`. The catch block only sets an error message — it does NOT clear the previous project's data. Net result: title flips to the new project, but `tasks` / `tasknotesById` still hold the previous project. UI renders "Frankenstein" — e.g., `<h1>Flowtron — fintown</h1>` over a row list that's actually bananapeel's. An error banner appears but is easy to miss above the chip row. Surfaces every time bug #1 fires. Fix shape: either pre-clear `setTasks([])` + `setTasknotesById(new Map())` at the top of `load()`, or fetch the three endpoints independently so a partial failure doesn't drop the whole load.
